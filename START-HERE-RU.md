# RelayKit: с чего начать

Учебный backend-проект на Go: принимает webhook-события, сохраняет их в SQLite, доставляет с подписью, повторяет временно неудачные запросы и позволяет повторно запустить dead letters. Это рабочий MVP для портфолио, а не подтверждение коммерческой эксплуатации.

## Запуск

Нужны Go 1.25.3 или новее, C-компилятор для SQLite/CGO и Python 3. CLI рассчитан на Linux/macOS; на Windows используйте WSL2. Перед реальным развёртыванием обновите Go и зависимости. Команды выполняются из папки проекта.

Самая короткая демонстрация:

```bash
python3 scripts/smoke.py
```

Скрипт собирает и запускает оба сервиса с временной БД и случайными секретами. Проверяет последовательность ответов **503 → 503 → 200**, отсутствие второго события при повторе ключа, конфликт 409 и сохранение истории после перезапуска. Нужны свободные локальные порты **18080 и 9090**. Скрипт завершает свои процессы и удаляет временные данные.

Для ручного просмотра создайте `.env` со случайными секретами:

```bash
python3 - <<'PY'
import secrets
from pathlib import Path
p = Path('.env')
if p.exists():
    raise SystemExit('.env уже существует; сохраните его или отредактируйте вручную')
p.write_text('RELAY_API_TOKEN=' + secrets.token_hex(32) + '\n'
             'RELAY_SIGNING_SECRET=' + secrets.token_hex(32) + '\n'
             'RELAY_ALLOW_LOCAL_DEMO=true\n')
p.chmod(0o600)
PY
set -a; . ./.env; set +a
go run ./cmd/receiver
```

Во втором терминале, из той же папки:

```bash
set -a; . ./.env; set +a
go run ./cmd/relaykit
```

В третьем терминале:

```bash
set -a; . ./.env; set +a
curl -s http://127.0.0.1:8080/v1/deliveries \
  -H "Authorization: Bearer $RELAY_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-order-1' \
  -d '{"destination":"http://127.0.0.1:9090/hook","payload":{"event":"order.created"}}'
curl -s http://127.0.0.1:8080/v1/deliveries \
  -H "Authorization: Bearer $RELAY_API_TOKEN"
```

Повторите первый запрос: вернутся тот же ID и `created: false`. Для подробной истории выполните `GET /v1/deliveries/ID` с тем же Bearer-токеном. Детали API и архитектуры — в `README.md` и `openapi.yaml`.

## Проверка и ограничения

В подготовленной версии прошли 11 integration/concurrency tests с race detector, `go vet`, сборка и живой smoke. После собственных изменений полезно повторить:

```bash
go test -race -count=1 ./...
go vet ./...
go build -buildvcs=false ./cmd/relaykit ./cmd/receiver
```

- Доставка **at least once**: после таймаута возможен повтор внешнего действия. Получатель должен сохранять обработанные `X-Relay-ID` вместе с бизнес-транзакцией. Карта в demo receiver хранится только в памяти.
- Один tenant, один worker в CLI и одна SQLite-БД на локальном диске. Бенчмарков и подтверждённой production-нагрузки нет.
- Нет пользовательских ролей, квот, retention, автоматических бэкапов, jitter, метрик и управления секретами отдельных получателей. Данные в БД не зашифрованы.
- По умолчанию разрешены публичные HTTPS-адреса; loopback HTTP включается только для демонстрации. Не публикуйте сервис с `RELAY_ALLOW_LOCAL_DEMO=true`.
- Docker/Compose и CI-конфигурация приложены; Docker и hosted CI в этой среде не запускались. Перед внешним доступом нужны TLS, ограничения нагрузки и эксплуатационная настройка.

## Пять вопросов перед собеседованием

1. Чем idempotency при enqueue отличается от exactly-once обработки у получателя? Где остаётся окно дублирования?
2. Как SQL-транзакция, lease и fencing token защищают очередь при конкуренции и падении worker?
3. Почему 503 повторяется, а 400 попадает в dead letter? Как backoff и `Retry-After` влияют на перегруженного получателя?
4. Почему проверки URL при enqueue недостаточно для защиты от SSRF? Как связаны DNS, IP-pinned dialer, redirect и TLS hostname?
5. Какие изменения и измерения нужны для нескольких серверов и более высокой нагрузки? Что стоит проверить до перехода на PostgreSQL?

## Как объяснять использование AI

Первая версия подготовлена с помощью AI. Не представляйте её как самостоятельно написанный production-сервис. Укажите, какие части вы лично прочитали, запустили, изменили и можете объяснить; пока этого не сделали, не утверждайте обратное.

После самостоятельного изучения можно сказать: «Это мой учебный проект, разработанный с помощью AI. Я проверил [конкретные сценарии], изменил [реальное изменение] и могу объяснить очередь, гарантии доставки и ограничения. Коммерческой эксплуатации у проекта пока нет».

Хорошая подготовка — самостоятельно добавить небольшой endpoint или изменить retry policy, написать проверку реального риска и объяснить результат по коду. Удалите скобки из примера только после такой работы.
